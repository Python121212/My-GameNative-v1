# 性能・発熱の解析：第1回

## 範囲と制約

対象は描画経路のソースコードです。CPU・GPU 使用率、フレーム時間、電力、温度や実ゲームを実機でプロファイルした結果ではありません。どこが実際に一番重いか、性能が何％向上したか、発熱が減ったかはまだ分かりません。Pixel 9a の GPU／ドライバーは GitHub Actions のエミュレーターでは再現されません。Mali Offline Compiler も本環境にはなく、実際の Mali 解析は未実施です。

## 調査で見つけた候補

| 経路 | コード上の観察 | 実測の状態 |
| --- | --- | --- |
| Vulkan（通常の描画経路） | `VulkanRendererContext.cpp` にフェンス待機、スワップチェーン取得・表示、転送やドロー処理がある | 各待機・処理の時間は未計測。待機は同期に必要な場合があり、削除しない |
| Vulkan のシェーダー | `window.frag` の FSR や HDR などは複数のテクスチャサンプルを使用する | 条件・端末ごとの GPU 時間は未計測。FSR/HDR の有効時以外にこの負荷があるとは限らない |
| OpenGL ES（VirGL 用） | エフェクト有効時、`EffectComposer.render()` はフレームごとに `setFilters` を各バッファと入力に呼ぶ | 同一設定の再送をコードで確認。GPU／CPU 時間は未計測 |
| OpenGL ES（VirGL 用） | エフェクト処理はオフスクリーンバッファと、エフェクトごとの描画パスを使う | 解像度やエフェクト数に依存。実機での時間・メモリ量は未計測 |
| CPU／メモリ／発熱 | ゲーム、変換レイヤー、ドライバー、端末設定などの影響を受ける | 実行時のボトルネックや温度の計測は未実施 |

なお、Vulkan レンダラーの `.so` は事前ビルド済みで、通常の APK ビルドでは C++ やシェーダーを再ビルドしません。ソースのシェーダーを変更するだけでは、配布 APK のネイティブ描画が変わるとは限りません。

## 今回の小さな変更

`Texture.setFilters` で、設定済みと同じフィルターを受け取った場合、OpenGL への再送を省略します。値の変更時とテクスチャの新規作成・再作成時は従来どおりパラメーターを設定します。対象は OpenGL ES 経路であり、標準の Vulkan 経路の高速化を意味しません。

**呼び出し数の理論値：** エフェクトが1つあり、3バッファと入力のフィルターがすべて前回と同じ場合、変更前は `setFilters` の4回の呼び出しで最大24回の GL 呼び出し（各回 bind 2回＋パラメーター設定4回）を行っていました。変更後はこの同一設定の送信が0回になります。フィルターを切り替える場合や、テクスチャ生成・再生成時は必要な呼び出しが残ります。これらはコードから数えた呼び出し回数で、FPS や時間の実測値ではありません。

## 検証方法

[GitHub Actions の ARM 変換エミュレーター](https://github.com/Python121212/My-GameNative-v1/actions/runs/43404812245)で3件のテストが成功しました。`TextureFilterOptimizationTest` は、同じ値の再送がないこと、変更時とテクスチャ再生成時に値が反映されることを OpenGL ES コンテキストで確認しています。ARM ライブラリの読み込みと基本描画テストも成功しました。エミュレーターによるテストは描画の回帰検査であり、実端末の性能試験ではありません。

## 次に測ること

同一のゲーム・場面・解像度・設定で、変更前後のフレーム時間（中央値・95パーセンタイル）、CPU／GPU 使用率、PSS、端末温度・電力を複数回測定します。ウォームアップ時間、充電状態、室温、開始時の温度も記録し、各試行前に安全にアプリのプロセスを終了してください。手順は [最適化の準備](最適化の準備.md) を参照。まず観測されたボトルネックに合わせて、変更を一つずつ追加・再検証します。
