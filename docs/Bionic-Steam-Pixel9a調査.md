# Bionic Steam の Pixel 9a 向け調査と測定

## 現状

この作業ではコードや既定設定を変更せず、調査と測定手順を用意した。Pixel 9a、Steam ログイン、Escape the Backrooms、オンライン・マルチプレイ、FPS・温度の実測は未実施。**最適化の効果は未確認**である。購入・ゲームの取得・認証の回避はしない。既存のゲーム、セーブ、APK、Steam データを削除しない。

Bionic Steam は実験的な機能で、ゲームの起動や接続は保証されない。Escape the Backrooms の協力プレイ・招待・音声・セーブの同期も未確認。発熱と FPS の改善は、同条件でゲームの正確性とマルチプレイを保った測定ができて初めて判断する。

## ソースからの候補（性能上の原因とは未確定）

1. `SteamBootstrap.prepareApp` は別プロセスのホストを起動し、最大60秒、100msごとに状態を確認する。この確認は起動時の経路であり、プレイ中の負荷を意味しない。ホストには認証情報を渡すため、環境変数・ホストの生ログを収集しない。
2. `QuickMenu` はゲーム内招待画面の要求を1秒ごとに問い合わせる。Bionic の場合は先に `SteamBootstrap.getProcessStatus()` で状態ファイルを読む。`SteamHostAchievementPoller` は実績を2秒ごとに問い合わせる。両者は機能が異なり、問い合わせを減らせば招待・実績が遅れたり失われたりする可能性がある。CPU／電力の影響は未測定。
3. `BionicSteamAssetsDependency.extractLsteamclientIntoPrefix` は互換性維持のため起動ごとに対象 DLL の展開・コピーを行う。起動時間や書き込みへの影響は未測定。単に省略すると、Proton 切替や破損後に不一致を残すおそれがある。
4. 招待処理は `SteamOverlayClient` のソケットを使用する。Steam 通信・ホストの処理時間、ゲーム／翻訳／描画との比率は未測定。ホストのネイティブ実装の一部はリポジトリに同梱されていないため、ソースだけで内部動作を評価できない。

ソース上の動作回数は、Pixel 9a の消費電力や FPS の測定値ではない。候補を採用する前に、基準・変更後の計測と招待／実績・再起動／Proton 切替の検査を行う。変更は一つずつ、必要に応じて元に戻せる形で行う。

## 実機での安全な基準測定

1. 正規に所有するゲームと GameNative をユーザー自身で起動し、Bionic コンテナと Bionic Steam を選択する。セーブのバックアップを先に確認。Steam ID、フレンド名、ログイン情報、トークンを共有しない。クローン環境では Steam・Pixel 9a に接続できない。
2. 正規ログイン後、まず単独で起動・描画・入力・音・終了を確認する。次に同意した相手との招待送信、受信、参加、10分以上の協力プレイ、再接続、ゲーム側で使える場合の音声を個別に確認する。各試験の失敗はそのまま記録し、ログインできない場合はまず起動・接続の解決を優先する。
3. 同一 APK・ゲーム版・設定・同一マップ、同じ人数・経路・時間、ネットワーク・充電・室温・明るさ・冷却条件で固定場面を用意する。ゲーム側や招待機能の条件が変われば公正な比較ではない。ゲームでの試験と OS 情報の読み取りはユーザーの承諾の下で行う。
4. 既存の [読み取り専用観測手順](次の最適化に向けた観測準備.md) でアプリの `dumpsys cpuinfo`、`meminfo`、`thermalservice`、`battery` を記録する。出力には名前や端末情報などが含まれ得るため Git やチャットに貼らず、共有前に必ず確認する。`gfxinfo` をゲーム FPS とみなさない。別プロセスのホストや Wine／ゲームはアプリ PID の監視だけでは特定・監視できず、出力や端末の権限を実際に確認する。FPS はゲーム描画に対応する別手段で計測し、未確認なら未取得と記す。
5. Baseline と候補を **A B B A A B B A** の順で各4回比較し、FPS／フレーム時間が取得可能ならその値、描画の正確性、開始・終了のバッテリー温度や端末が報告する熱状態、動作時間、試行の失敗を記録。4サンプルを4試行と混同しない。負荷の取得や温度の取得に失敗した場合は未測定とし、推測しない。
6. 観測自体の影響をオン／オフで確認。長時間の安定性は短い4試行とは別に確認し、熱警告や異常時は中止。ゲーム起動しない、招待が届かない、参加できない、クラッシュする等の機能回帰があれば候補を採用しない。セーブや認証・オンライン機能に変更を加えない。

## 改善候補の判定

- 起動準備の展開・コピーが実測で支配的なら、内容・版・宛先を確実に照合して不要な処理を避ける案を検討。破損、途中中断、同一サイズの異なるファイル、Wine/Proton 切替やロールバックを含むテストが必要。安全性が証明できない場合は従来どおり展開する。
- 招待・実績のポーリングが実測で負荷源なら、機能を維持するイベント駆動または待機の調整を検討。招待の見逃し・遅延、実績の重複・消失、ホスト再起動や複数要求について検査する。測定前に間隔を変更しない。
- GPU やゲーム側が支配的なら Bionic Steam 自体の変更で FPS が改善するとは限らない。[Escape the Backrooms の調整準備](Escape-the-Backrooms調整準備.md) に沿って別途切り分ける。FEXCore のキャッシュ正常性は引き続き未検証。

エミュレーターの基本起動・描画試験やモック試験は実ゲームの Steam 接続／Pixel 9a の性能の代わりにはならない。実行可能な APK の更新を行う場合は、署名・データ保持に注意し、インストール前に必ずユーザーがバックアップを確認する。
