# 二重変換の調査と回避

## 現在分かっている経路

- Bionic 起動の ARM64EC Wine では、通常 `HODLL` に FEX の `libwow64fex.dll` または `wowbox64.dll` のいずれか一つを選択し、Wine を直接起動する。両者を直列に実行する構造はこの選択コードでは確認できない。非 ARM64EC の通常経路は Box64 を前置する。独自の起動コマンドによる上書きもあるため、ソースの確認だけでは実際に読み込まれた DLL や全経路を証明できない。
- Android 描画 CI は x86_64 エミュレーター上で ARM ライブラリの変換を使う。Windows x86-64 → ARM64 の変換器をそこで動かすと、エミュレーター側でも ARM コードの変換が必要となり、性能・発熱の比較には適さない。この CI は機能・起動の回帰検査として残す。
- ARM64 Linux runner 上の FEX／Box64 試験は上記の x86 Android エミュレーターを介さず動作するが、Android 用 FEXCore／WOWBox64、Pixel 9a やその GPU を再現しない。Linux の結果を Android の実測としない。

## 対象端末の非破壊確認

adb 接続された明示的な端末について、以下で ABI、カーネル、Native Bridge、エミュレーター属性を表示する。インストール、アプリ停止、ファイルやキャッシュの消去はしない。シリアルをログや公開文書に記載しない。

```sh
adb devices
./tools/translation-benchmark/check-android-translation.sh '端末のシリアル'
```

ARM64 ネイティブ「候補」はプロパティ上の目安であり、仮想化や実際のプロセスでの翻訳の不在を証明しない。端末の実体と、対象プロセスで読み込まれた Wine・変換器ライブラリを別途確認する。独自起動コマンド、32 ビットの処理、追加のブリッジはこのスクリプトでは判定できない。未確認なら性能比較として扱わない。

## 解消に向けた条件

ARM64 Android 実機または実行経路を確認できる ARM64 環境で、対象 APK と同一の Windows ベンチマークを使って FEX／WOWBox64 をそれぞれ実行する。起動・描画・正確性とロードした変換器を確認し、[比較記録](最適化比較記録-ひな形.md)に各4回の測定と温度を記録する。これにより x86 Android エミュレーター側の追加変換を避けられるが、Windows コード自体の変換や Wine の処理は残る。

GameNative の変換経路を短縮したこと、FPS や発熱が改善したことはまだ実証できていない。Linux 版 FEX キャッシュは出力不一致のため解決前に有効化して性能を評価しない。Android 版キャッシュの挙動も別途検証する。詳細は [命令変換ベンチマーク計画](命令変換ベンチマーク計画.md) を参照。
