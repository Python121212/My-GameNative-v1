# Freedoom を使った DXVK コード変更の連続4試行

## 結論

DXVK 2.6.1 の D3D9 `Present` 経路について、4つのコード変更候補を順番に実装・ビルド・測定した。**4候補とも明確な FPS 改善は確認できなかった。** 先行候補の効果が不明だったため、変更を積み重ねず、各候補を未変更の同一ソースと個別比較した。したがって、4つの成果を積み重ねた完成版の改良ではない。いずれも試験用パッチとして保存し、GameNative の DXVK や既定設定には採用していない。WineD3D のコード改良は今回行っていない。

## 方法

DXVK `v2.6.1` のコミット `2b1a284f8453baa2bd193709b67e5183074c74ba` とそのサブモジュールを取得。未変更とパッチ適用後の d3d9.dll を同じ runner・コンパイラ・ビルド設定でビルドし、それぞれ Chocolate Doom 3.1.1＋Freedoom 0.13.0 の DEMO1 をウォームアップ後4回実行した。比較条件は同一 runner 内で交互に、2回ごとに順序反転。DLL ロードと SDL Direct3D 9 レンダラーを確認。各候補を試す前に前回の結果を確認した。

対象は Linux x86-64 Wine 上の Vulkan lavapipe ソフトウェア描画であり、SDL の診断用プロキシによる固定フレーム読み戻しを timedemo 中に含む。各比較は別 runner のため、比較間の絶対 FPS は直接比較しない。FPS はゲームの timedemo 表示値であり、GPU 実行時間や消費電力の測定ではない。

候補ごとの4回値は小数点第4位で丸め。変化は各回のばらつきに比べ小さく、この測定では改善と判断できない。各試行は 2664 gametics で完走し、固定フレーム120の RGB SHA256 は全32試行で `2342af2ac6da4d8b3048b9268e4ec6a58c73c4215076824656640d4c8c124cbe`。1フレームだけの比較で、リサイズ・ウィンドウ切替・フルスクリーン・HDR 等や、すべてのフレームの正確性は検証していない。これらの状態変更や複数ウィンドウを含む専用テストが採用前に必要。

各候補のソース差分は `tools/graphics-benchmark/patches/dxvk-present-*-cache.patch` にある。再現用 workflow は `.github/workflows/freedoom-dxvk-code.yml`、各実行時点のコミット `a3829ae`、`e6e043b`、`f365a08`、`927cc8e` を参照。試験用 DLL は一時領域で使用し、既存 APK やゲームデータには触れていない。結果を本体に導入する変更でもない。各実行のログと画像は Actions に14日間保存。

## 今後の課題

Present 内のどの待機・処理が支配的かは未分離。上記の小さな CPU 処理削減ではその待ち時間自体は解消されない。適切なトレースで acquire・同期・コマンド実行・表示の内訳を測り、WineD3D の Lock／Unlock も別途調査する。Android・Pixel 9a、実 GPU、発熱、共有メモリの実測は未実施。
