# Freedoom の画面転送と表示の計測

## 対象と測定方法

[実行 43551551121](https://github.com/Python121212/My-GameNative-v1/actions/runs/43551551121) で、Windows x86-64 の Chocolate Doom 3.1.1 と Freedoom 0.13.0 の同じ `DEMO1` を、Wine 上の DXVK 2.6.1 と WineD3D で実行した。環境は GitHub Actions x86-64 Linux、Vulkan lavapipe／OpenGL llvmpipe による**ソフトウェア描画**、Xorg dummy 画面。Android・Pixel 9a・GameNative の測定ではない。GPU 実機、発熱や共有メモリ使用量は計測していない。

SDL2 の試験用プロキシで、ゲームから呼び出された SDL API の前後を `QueryPerformanceCounter` で測り、各呼び出し内の**CPU 側の経過時間**を集計した。CPU の実使用時間や GPU 実行時間ではなく、ドライバー内の処理・待機・スケジューリングも含まれる。SDL 内部から行われる呼び出しのすべてを捕捉する仕組みではない。計測した関数は texture lock、色変換等を伴う lower blit、unlock、レンダーターゲット切り替え、render copy、present。各呼び出しの経過時間を足したものは、ゲーム全体や GPU で費やした時間ではない。

先頭30回と画像読み戻しを行った120回目の表示を対象から外し、1試行あたり 2673 回の Present に対する各関数の合計時間を割った。試行中のその他の処理はこの表に含まれない。各方式について事前実行後、計時オン／オフの各条件を順番を回転させて4回ずつ実行した。画面診断プロキシは両条件とも使用し、読み戻しはデモ時間には含まれるが関数時間の集計からは除いた。各条件の固定フレームの RGB は一致し、デモのゲーム進行は各回 2664 gametics。1フレームの一致だけではすべての描画の正しさを保証しない。

## 関数別の結果

4回の「対象フレームあたり CPU 側経過時間」の算術平均。複数回呼ばれる関数の値も、そのフレームあたりの合計を示す。

| SDL の処理 | DXVK | WineD3D |
|---|---:|---:|
| テクスチャ Lock | 0.0023 ms | 0.5168 ms |
| LowerBlit | 0.0386 ms | 0.0259 ms |
| テクスチャ Unlock | 0.0011 ms | 1.5231 ms |
| 描画先の切り替え | 0.0051 ms | 0.0070 ms |
| RenderCopy | 0.0536 ms | 0.0316 ms |
| **RenderPresent** | **3.9376 ms** | **1.9153 ms** |

この環境で今回測った API のうち、DXVK では `RenderPresent`、WineD3D では `RenderPresent` とテクスチャ `Unlock` の経過時間が大きかった。WineD3D の Lock と Unlock を合わせると約 2.04 ms／対象フレーム。**どこで実際に同期しているか、転送・処理・待機それぞれの内訳や原因はこの数値だけでは分からない。** GPU 待機だと断定しない。ゲームの CPU 描画、計時対象外の呼び出しや他のプロセスは表に含まれない。

Lock 時のテクスチャ形式・矩形から算出した論理上の画素データは、各試行で合計 684,288,000 バイト、対象 Present あたり平均 256,000 バイト（320×200×4）。これは **実際にコピーされたバイト数、GPU バス転送量、VRAM 使用量、帯域ではない**。パディング・キャッシュ・内部コピーは別途測定が必要。

計時の影響を調べるため、同じプロキシで計時をオフにした条件と比較した timedemo FPS の各4回平均は、DXVK オフ 156.134／オン 156.779、WineD3D オフ 207.701／オン 208.283。各回のばらつきがあるため、この比較は計時のオーバーヘッドがゼロであることを意味しない。タイマー・関数転送・テクスチャ情報の問い合わせは実行に影響し得る。個々の値、CSV、画像と環境情報は Actions 成果物 `freedoom-profile` に保存（14日間）。

## 次の調査候補

- DXVK は Present の中の待機・ドライバー処理、WineD3D は Lock／Unlock 内の待機やアップロード経路を、対応するトレースツールやライブラリ内部の追加計測で分ける。まず再現性と描画の正しさを確認する。
- Direct3D 9 の表示経路の結果を Direct3D 11 や GPU 主体のゲームに一般化しない。既定設定の変更、FPS 向上や低発熱の主張はしない。
- 実機または適切な ARM64 Android 環境では GPU の計測手段、フレーム時間分布、温度、利用可能な共有メモリ指標を別に確認する。FEX キャッシュの正確性問題も未解決。
