## 描画の確認

### 発生した問題と対応

- ビルド時に Kotlin のメモリ不足が起きたため設定を変更し、その後の APK ビルドは成功した。
- 描画の変更後、エミュレーターで APK 起動数秒後に GPU 情報取得のネイティブクラッシュが発生した。GPU 列挙失敗時の処理を安全化し、独立した JNI ライブラリを使用するよう修正した。[修正後の実行](https://github.com/Python121212/My-GameNative-v1/actions/runs/43413964189) では5件のテスト、起動、前面表示、10秒間の生存を確認した。長時間動作や実機での安定性は未確認。
- ARM Linux の Wine 実験では proot 経由で変換器がクラッシュし、直接の rootfs・ライブラリパス指定で回避した。Box64 の新規 Wine 環境の初期化は当初タイムアウトしたが、設定を調整した[実行](https://github.com/Python121212/My-GameNative-v1/actions/runs/43434043199)で FEX の設定をコピーせず Windows 版 7-Zip の実行に成功した。タイムアウトの根本原因は未特定。
- Linux 版 FEX の配布パッケージには必要なオフラインコンパイラーがなかったため、同じ固定ソースからビルドして試験した。キャッシュの生成・ファイルの mmap は確認したが、キャッシュ有効時の最小プログラムは期待した出力をせず、ゼロ長 write を行った。無効時は正常で、内蔵照合はクラッシュした。ブロック結合の無効化でも解消せず、原因・修正は未確定。[詳細と試験結果](命令変換ベンチマーク計画.md)を参照。ファイルの存在や読み込みだけでは正しい実行を示さない。

### 現在の状態と次の作業

- [PR #12](https://github.com/Python121212/My-GameNative-v1/pull/12) は調査中のドラフトで、FEX キャッシュ検査は失敗したまま。今回の調査記録と変更は main に未反映であり、正常動作を確認せずにマージしない。

- 次の最適化の前に、FEX キャッシュの正確性を引き続き調査し、無料 CPU ベンチマークを同条件で FEX／Box64 各4回測る。結果の正しさと各回の値を記録し、変更後に同条件で再測定する。改善を確認できた場合に限り SuperTuxKart に進む。これらの比較はまだ行っていない。

## Direct3D 描画の予備比較

無料の自作 D3D9／11 合成試験を準備し、x86-64 Linux のソフトウェア描画で DXVK と WineD3D を各4回比較した。[詳細と数値](Direct3D描画の予備比較.md)を参照。これは Pixel 9a／GameNative やゲームの実測ではなく、実機の優劣、温度、メモリの改善は未確認。

## 無料ゲームの描画比較

Freedoom と Chocolate Doom の固定デモを用いて、DXVK／WineD3D を各4回比較し、1フレームの画面一致を確認した。[詳細](Freedoom無料ゲームの比較.md)を参照。x86-64 Linux のソフトウェア描画上の Direct3D 9 表示経路であり、Android 実機、Direct3D 11 やゲーム全般の性能ではない。

## Freedoom の描画設定候補の再測定

DXVK のフレーム待ち数と WineD3D の CSMT を別々に変更し、既定設定と同じ runner で各4回比較した。[結果と制約](Freedoom無料ゲームの比較.md)を参照。DXVK は明確な改善を確認できず、WineD3D は限定条件で平均が高かったが、Android 実機での効果・発熱は未確認のためいずれも既定設定には採用していない。

## Freedoom の転送・表示時間

SDL 呼び出しの CPU 側経過時間を DXVK／WineD3D で4回ずつ計測した。[計測方法・結果・限界](Freedoom転送と表示の計測.md)を参照。DXVK では Present、WineD3D では Present とテクスチャ Unlock が計測対象の中で大きかったが、待機・GPU 実行・実転送量の内訳は未特定。ソフトウェア描画の結果であり、Pixel 9a の実測ではない。

## Freedoom の改善候補：4比較

DXVK の2設定と WineD3D の CSMT 無効化の独立再検証2件を実施し、各比較で基準と候補を各4回測定した。[結果](Freedoom改善候補4比較.md)。DXVK の明確な向上は確認できず、WineD3D の小さい上昇は実機で未確認。設定試験であり、4回の連続したコード最適化やアプリ既定値への採用は行っていない。

## DXVK コード変更の連続4試行

Present 経路の4候補を1つずつ実装し、それぞれ元の DXVK と Freedoom 各4回で比較した。[方法・各回・制約](Freedoomコード改良4回.md)。どの候補も明確な性能改善は確認できず、本体には未採用。WineD3D のコード改良や Android 実機での効果は未検証。

## 独自 Direct3D 互換レイヤーの開発開始

`experimental/gamenative-d3d9/` に Vulkan の RGBA8／BGRA8 画像転送基盤を独立実装した。複数の更新のまとめ送信、永続マップ、フェンスを使った再利用、非コヒーレントメモリ対応と読み戻し検査を備える。基盤の検査は [43556936692](https://github.com/Python121212/My-GameNative-v1/actions/runs/43556936692) で lavapipe・validation layer にて成功。まだ D3D9 の COM や DLL・描画・Present はなく、ゲームを動かせない。既存アプリや APK には未統合。FPS・実機性能の比較は行っていない。[詳細](../experimental/gamenative-d3d9/README.md)。

## 独自 Direct3D レイヤーの続き

BGRA8 の CPU コピーを持つ D3D9 風ロック・部分更新・転送領域に収まらない更新の分割を追加。実験用 Windows DLL に `Direct3DCreate9` 等と COM の入口を追加し、未対応のデバイス作成は失敗させる。Vulkan・Wine のテストは [43557611104](https://github.com/Python121212/My-GameNative-v1/actions/runs/43557611104) で成功。DLL と Vulkan 基盤は未接続であり、ゲームは動かせない。APK や実機の性能は未検証。[実装と制限](../experimental/gamenative-d3d9/README.md)。

## Direct3D 10 の基本動作確認

DXVK と WineD3D を別 runner の x86-64 Linux Wine ソフトウェア描画で各4回検査し、D3D10 デバイス作成・赤い三角形の描画・Present の戻り値を確認した。詳細と限界は [Direct3D 10 動作確認](Direct3D10動作確認.md)。Android 実機・実ゲームでの動作は未確認。

## Direct3D 10 の FPS 予備測定

同一 runner で合成三角形を各4回測定し、DXVK 平均 1552.544、WineD3D 平均 2361.358 FPS。[条件と制約](Direct3D10動作確認.md#基本描画の-fps-予備測定)を参照。短いソフトウェア描画試験であり、実ゲームや Android 実機の FPS ではない。
