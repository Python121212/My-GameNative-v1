# Pixel 9a：性能・メモリ・発熱・入力遅延の調査計画

## 重要：測定前の状態

Pixel 9a 固有の速度向上、消費電力低下、RAM 節約、DX11、フレーム生成の動作・遅延、バックグラウンド復帰は**実機未測定**。この文書と LSFG 設定の注意書き以外に性能動作の変更はない。どの方法も改善確定ではない。既定値や既存ゲーム・セーブは変更しない。試験版 APK のみ更新する。Pixel 9a は Tensor G4・RAM 8 GB・60〜120 Hz 表示であり、8 GB 全部をゲームが使えるわけではない（[Google 製品仕様](https://store.google.com/jp/product/pixel_9a_specs?hl=ja)）。

## ソースからの現状と優先順位

1. **起動・正確性優先。** `XServerScreen.kt` と `LsfgVkManager.kt` に既存の LSFG 経路がある。後者のサポート判定は Bionic コンテナかどうかを見ており、Pixel 9a の GPU 互換性を証明しない。Lossless.dll の入手は本人の正規環境に限る。フレーム生成は既定で強制しない。
2. **RAM とマルチタスク。** `MainActivity` の非表示時画像キャッシュ解放と、圧縮試作のキャッシュ解放は既存。後者はゲーム未接続で、swap 拡張ではない（[接続調査](圧縮ファイルと仮想メモリの接続調査.md)）。圧縮キャッシュだけを解放してもゲームや他アプリの生存は保証されない。UI だけでなく Wine・ゲーム・ホストなど対象プロセスを個別に把握して PSS 等を比較する。Android 14 以降、キャッシュ状態のバックグラウンド処理は制限され、メモリ圧迫時に停止され得る（[Android の変更](https://developer.android.com/about/versions/14/behavior-changes-all)）。OS の制限や他アプリを強制終了して回避しない。重要なゲームデータの保存はゲーム側に任せ、復帰不能を前提にセーブを保護する。
3. **DX11。** DXVK は D3D11 を Vulkan に変換する既存経路。WineD3D とゲーム単位で同じ描画と機能を確認して比較する。GPU ドライバー・Vulkan 機能・DXVK 版により結果は変化する。シェーダーコンパイルやキャッシュがスタッターに関係する可能性はあるが、バージョンで方式は変わる（[DXVK 2.4](https://github.com/doitsujin/dxvk/tree/v2.4)、[DXVK リリース](https://github.com/doitsujin/dxvk/releases)）。データを削除して試験しない。実ゲーム DX11 の基準測定なしにパッチや DLL を切り替えない。
4. **熱と電力。** `SessionReport` は熱状態・対応端末の headroom を記録でき、`AdaptiveFpsCapController` は有効なプロファイル等の条件で FPS 制限を調整する。これらが Pixel 9a と対象描画経路で有効・正確とは未確認。Android の熱 API は端末依存であり、無効値を正常と決めつけない（[Thermal API](https://developer.android.com/games/optimize/adpf/thermal)）。FPS 制限や解像度変更は入力応答と品質を下げ得るので任意で比較する。充電条件・室温・輝度を固定し、端末が熱い場合は試験を中止する。
5. **生成フレームと応答。** 生成画像は入力を処理した新規ゲームフレームではない。例として実フレーム 30 FPS の間隔は約33.3 ms、60 FPS は約16.7 ms。生成して表示回数が増えても 30 FPS 時のゲーム更新間隔は 60 FPS にならず、追加処理・待機で遅延やゴーストが増える場合がある。逆に表示の滑らかさは改善する可能性がある。入力遅延は FPS から確定できず、60 FPS でも総遅延が 16.7 ms という意味ではない。LSFG 無効を入力重視の基準にし、実フレームが安定した場合に限って任意で 2倍を比較。Pixel 9a で動作や改善が証明されるまでは推奨設定として強制しない。

## 実機で行う比較（未実施）

- 先に正規所有のゲーム、セーブのバックアップ、起動・表示・操作・音・終了を確認。オンラインやマルチプレイは別に確認し、認証情報やゲームファイルを送信しない。無料ゲームでの予備検証も行う。[Escape the Backrooms の準備](Escape-the-Backrooms調整準備.md) を参照。
- 同一 APK・ゲーム版・場面・解像度・充電状態・明るさ・室温・ネットワークを固定。各候補は一つずつ、A B B A A B B A の順に各4回。短期試験のほか、冷却状態から長時間試験を別に実施し、失敗も記録。前回の FEX/Box64・描画試験の未完項目は [命令変換ベンチマーク計画](命令変換ベンチマーク計画.md) 等に残る。
- 実ゲーム由来 FPS とフレーム時間（平均・低下・1% low、取得条件を記載）と描画の正確性を確認。Android UI の描画 FPS や生成後の表示 FPS を実ゲーム FPS と取り違えない。LSFG の有無はゲーム実 FPS、表示 FPS、熱、バッテリー消費、画質、入力から画面反応までを別々に比較。入力遅延は可能なら入力と画面を同時に高速度撮影して複数回測る。手段がない値は未測定とする。
- 熱状態とバッテリー温度は別指標。電力は対応する外部計測器等で測るか、長時間のバッテリー減少を同条件で比較し不確かさを明記する。CPU/GPU 使用率とアプリ・ゲーム関連プロセス PSS が取得できるか確認する。診断の負荷自体も比較し、個人情報を確認するまでログを共有しない。
- バックグラウンド試験は保存後、同じ手順・待機時間でアプリ切替→復帰を行い、各プロセスの終了・再起動・セーブ復元・通信を記録。システムの制限・LMK とアプリ側クラッシュを区別する。OS の動作は保証しない。

採用基準：描画・入力・セーブ・通信に回帰がなく、複数回の測定で安定した効果があり、温度・電力・遅延の悪化を説明できること。エミュレーターの基本起動・描画検査は Pixel 9a の GPU・熱・電力・性能を再現しない。
