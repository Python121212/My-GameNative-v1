# 共有メモリと描画経路の調査

## 経路とコピー

- OpenGL の VirGL では `VirGLRendererComponent.flushFrontbuffer` が描画済み framebuffer を `Texture.copyFromFramebuffer` でテクスチャにコピーし、`GLRenderer` がそのテクスチャを描画する。コピー自体は残る。CPU 描画の Drawable では direct ByteBuffer と GL テクスチャがあり、初回 `glTexImage2D`、更新時 `glTexSubImage2D` でデータを渡す。
- OpenGL のエフェクト処理では、sceneBuffer と、パス数に応じた中間 RenderTarget にそれぞれ色テクスチャを確保する。既存の変更では1パス時の不要な中間2枚を避けるが、ゲーム全体や Vulkan のメモリ使用量は示していない。
- `VulkanRendererContext` の通常の CPU 入力経路はウィンドウ用 staging メモリに行ごとに `memcpy` し、コマンドバッファで画像へ `CmdCopyBufferToImage` する。一方、AHardwareBuffer の経路では Vulkan にインポートしてキャッシュする。画像の所有権、フェンス、寿命とメモリ可視性が関係するため、同じものとして扱ってコピーを消してはいけない。scanout カーソルにも CPU コピーがある。LSFG・XR はさらに別の画像やバッファを使用する。
- これらはソース上で確認した経路であり、実際のゲームがどの経路を使い、ドライバー内部に何個の割り当てやコピーがあるかは未測定。Android の CPU／GPU は物理メモリや帯域を共有しうるが、アプリの割り当てがそのまま実メモリ増加量に一致するとは限らない。

## 今回の限定的な変更

VirGL の framebuffer コピーでは、従来は毎回 `glCopyTexImage2D` で保存領域を再定義していた。初回・サイズ変更・破棄／コンテキスト喪失後は引き続き再定義し、同じ正のサイズでの以後のコピーには `glCopyTexSubImage2D` を使用する。データの転送は残るため、コピー帯域や実際の割り当て削減量は未測定。GPU ドライバーや同期の違いによって効果が変わり得る。

[Android エミュレーター試験 43540614062](https://github.com/Python121212/My-GameNative-v1/actions/runs/43540614062) は、新規 EGL テストを含む6テストと APK の起動・前面表示・10秒生存に成功した。新規テストは同サイズでの再利用、赤／緑のピクセル、サイズ変更と破棄後の再作成を検査する。x86_64 エミュレーターの ARM 変換環境であり、実機の VirGL ゲーム、複数 EGL コンテキストの同期、Vulkan、FPS・温度・メモリ削減は未検証。性能改善と断定せず、実機や対応 ARM Android 環境で確認する。

## FEX キャッシュの並行調査

[Linux FEX 検査 43541636930](https://github.com/Python121212/My-GameNative-v1/actions/runs/43541636930) では、従来の文字列出力テストはキャッシュ無効なら正常、有効ではゼロ長 write、照合モードでは SIGSEGV となり、全体は失敗した。

追加で、算術による終了コード42、およびメモリ操作と分岐を伴う終了コード42の2種類の ELF を検査した。記録・生成・無効対照・有効実行はそれぞれ42で、キャッシュファイルの mmap も確認した。ただし mmap はキャッシュ命令そのものの実行証明ではなく、これらの成功で元の不具合が解決したわけではない。最初の補助試験では FEXServer が UID 単位の抽象ソケットを共有し、HOME の変更だけではサーバーを分離できなかったため、各試験固有のソケットを設定して再実行した。これは自前ビルドの ARM Linux FEX に限られ、Android 版の動作は別途確認が必要。

FEX の不具合の原因・修正は未確定。キャッシュ有効時の正しい出力、キャッシュ命令の実行と幅広い正確性が検証できるまで性能比較の成功条件を満たさない。[命令変換ベンチマーク計画](命令変換ベンチマーク計画.md)を参照。
