# Escape the Backrooms 向けチューニング準備

## 状態と目的

容量削減やクラウドの実装は保留。ここでは正規に入手した Escape the Backrooms（Steam App ID `1943950`）を対象に、**起動と描画の正確性を優先**し、Pixel 9a などの実機で FPS と発熱を比較する手順を準備する。ゲームの購入・取得、実行、オンライン接続、FPS・温度の測定は今回していない。最適化済みの設定はまだなく、効果は不明。

[Steam の公式ストア](https://store.steampowered.com/app/1943950/Escape_the_Backrooms/) は Windows 64-bit、DirectX 11、最小 8 GB RAM、25 GB の空き容量などを記載している（2026年11月確認）。要件は更新され得る。DirectX 11 の表記は実際の GameNative 上の使用 API、起動や FPS を証明しない。ゲームは有料なので購入せず、所有者が正規にインストールしたもののみでテストする。

ユーザーから Unreal Engine 4 製との情報があり、[PCGamingWiki](https://www.pcgamingwiki.com/wiki/Escape_the_Backrooms) にも UE4 の記載がある。実際に試すゲームの版とエンジンの詳細は未確認。UE4 向けの一般設定がすべて本ゲームに効くとは限らない。

### UE4 を踏まえた準備

- まずゲーム内で利用可能な解像度・画質・影・描画距離などの項目を実際に確認し、存在する項目だけを1つずつ比較する。項目の有無・効果は未確認。
- テクスチャストリーミング、シェーダーの初回生成、照明・影や描画解像度が負荷の候補になり得るが、現時点ではどれが原因か不明。初回とウォーム後を分けて観測する。
- 設定ファイルやコマンドライン引数、UE4 のコンソール変数を勝手に追加・変更しない。ゲーム内設定で検証できない仮説を試す際は、対象バージョンでの対応と元設定への復元を確認し、事前にユーザーの許可を得る。セーブやマルチプレイに影響する変更は避ける。

## 事前に記録する

- ゲームのバージョン・更新日、Steam のビルド ID（確認可能な場合）。ライセンス情報・認証情報・端末のシリアルは記録に含めない。
- 端末名、Android・GPU・ドライバーバージョン、画面リフレッシュレート、解像度、温度の種類と単位、充電状態と残量、室温・ケース・冷却条件。
- GameNative APK の版・SHA-256、Wine/Proton、変換器（FEXCore / WOWBox64 等）と版、描画ドライバー、DirectX ラッパーと版、コンテナ・表示設定、ゲーム内設定、フレーム制限・VSync、起動引数。分からない項目は「未確認」。
- FPS の計測元と期間。GameNative の FPS 表示、ゲーム内表示、DXVK HUD 等の値が存在しても、その表示対象・更新間隔・負荷を確認するまではゲームの真の平均やフレーム時間と断定しない。画面録画で値を記録する場合も録画負荷を別途比較する。自動収集できなければ表示値と時刻を手動記録し、フレーム時間・1% low は未取得とする。
- 変更前に元の設定を記録し、復元手順を確認。セーブ・ゲームデータ・既存 APK・キャッシュは勝手に削除しない。別コンテナや別セーブを使う場合も、Steam / Wine のデータ共有や更新の影響を確認し、ユーザーの許可なく既存データを移動・消去しない。ゲームファイルを改変しない。

## 起動と固定場面の準備

1. ゲームの所有者が正規の方法でインストールし、現状の設定で起動する。ログイン情報を記録・共有しない。起動しなければ、ステージ、エラーの種類、クラッシュ時刻を残し、性能比較より修正を優先する。ライセンス、オンライン認証、保護機構を回避しない。
2. タイトル、メニュー、実際の3D場面で描画、文字、入力、音、クラッシュの有無を確認する。最初は他プレイヤーに影響しない個人の場面を選ぶ。オンライン機能は別途、所有者の同意と正常なログインのもとで確認する。
3. 固定場面 A は、プレイヤーの位置・視点を固定した静止画面。固定場面 B は、同じ開始位置・視点からタイマーに沿って同じ経路を移動する。実際の地点・操作・時間はゲームで確認して記録する。ランダムな敵、他プレイヤー、ロードや進行状態が違う場合は条件差として記録し、同一比較と見なさない。場面が再現できなければ測定を延期する。
4. 描画欠落・黒画面・文字化け・入力不良・落下や進行不能があればその試行は失敗。比較用スクリーンショットは同じ地点で撮り、ユーザー名や他人の情報が写っていないことを確認してから共有する。

## 基準計測

- 起動・ロードを完了し、事前に決めたウォームアップを行う。初回シェーダー生成やキャッシュ状態は別に記録し、初回とウォーム時を混ぜない。キャッシュを消す実験は既存データで行わない。
- 各試行の開始温度・終了温度、残量、FPS 表示の読み、計測時間、画質・異常終了を記録する。温度が未取得なら未取得とする。ゲーム FPS と Android UI の `gfxinfo` を混同しない。
- それぞれの比較で基準 A と候補 B を **A→B→B→A→A→B→B→A** の順に各4回、同一場面・設定で行う。各試行間は、可能なら同じ温度域に戻してから開始し、待ち時間を記録。再現可能な温度条件が作れなければ結果の制約として残す。長時間の熱安定性は4回の短時間試行と別途確認する。
- 各4回を独立した試行として記録し、成功した条件のみ平均・範囲を報告。ウォームアップや `collect.py` の4サンプルを4試行と数えない。失敗は除外して成功と見せず原因と件数を記録。
- 過熱警告、著しい温度上昇、充電異常、動作異常があれば中断。安全温度は端末が報告する状態に従い、未取得のセンサーを推測しない。

## 段階的な候補（採用前の仮説）

1. **ゲーム内の描画負荷**：使用可能な解像度または画質の項目から1項目だけ変更。FPS、画質、温度と入力のしやすさを確認する。項目や変更効果は実機で確認するまで未確定。
2. **フレーム上限**：ゲーム内または GameNative に選択肢がある場合に1項目だけ変更。上限を下げて温度やカクつきが減るかを比較する。最大 FPS が高いことだけを採用条件としない。
3. **DXVK と WineD3D**：実際に選択可能で、同じゲーム内描画 API で動く場合に比較。描画経路・GPU 互換性が異なり得るため、起動・画面の正確性を先に検査する。WineD3D で動くことは未確認。DX12 を利用している場合は同じ比較として扱わない。
4. **変換器**：正しい起動・出力を確認した上で FEXCore と WOWBox64 を個別に比較。Wine の版・アーキテクチャなど変更できない条件も明記し、完全に同一条件にできない場合は限界を併記。Android の FEXCore キャッシュは実読込・正常動作未検証で、Linux FEX の問題をそのまま一般化しない。`FEX_ENABLECODECACHINGWIP` の有無だけではキャッシュ利用の証拠にならない。

いずれも**1回に1要因**。4候補は順次検討し、比較が成立しない候補は未実施と記録する。実装や環境変数を事前にゲームへ強制せず、効果・互換性を示すまでは既定設定に採用しない。共有メモリは CPU/GPU の転送・割当を実機で確認する別課題で、PSS を GPU 共有メモリ使用量とみなさない。

## 読み取り専用観測

[観測準備](次の最適化に向けた観測準備.md) の `tools/optimization-observer/collect.py` を必要に応じて使う。シリアルはローカルで指定し、出力は新規ディレクトリに保存し、共有前に個人情報を確認する。PID 判定はゲームの別プロセスの生存を保証しない。収集そのものの負荷も検討する。

```sh
adb devices
# 自分で対象の場面を起動してから。出力先は存在しないディレクトリ
python3 tools/optimization-observer/collect.py \
  --serial '端末のシリアル' --output ./escape-observation-01 \
  --samples 4 --interval 10
```
