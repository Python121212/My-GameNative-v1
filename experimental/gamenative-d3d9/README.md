# GameNative 独自 Direct3D 9 互換レイヤー：実験基盤

## 現在の実装範囲

これは独自の互換レイヤーを作るための**実験用部品**であり、完成した Direct3D 9 互換 DLL ではない。ゲームに読み込ませることはできず、Freedoom や GameNative ではまだ動作しない。DXVK や WineD3D のコードは含まず、両者の機能を自動的に併用・切替するものでもない。FPS 向上は未測定・未保証。既存 APK、Wine、ゲームデータの変更や置換はしない。

実装しているのは、単一スレッドで使う Vulkan のオフスクリーン RGBA8／BGRA8 テクスチャ転送、D3D9 の一部のロック動作を模したフロントエンドと、別個の実験用 DLL 入口：

- 実験用 DLL は `Direct3DCreate9`／`Direct3DCreate9Ex` と `IDirect3D9` の COM の入口だけを持つ。アダプター数は0で、デバイス作成は未対応として失敗を返す。Vulkan 転送基盤とはまだ接続していない。実際のゲームの `d3d9.dll` として使用しない。
- Vulkan インスタンス・デバイス・描画キュー、画像、永続的にマップしたステージングバッファを管理。
- 矩形の lock/unlock 風 API で CPU 書き込み領域を確保し、複数の画像更新を一つのコマンドバッファ・一回のキュー送信にまとめる。部分更新と重複する更新の順序を保持。
- 送信自体は GPU 完了を待たず、次にステージング領域を再使用する前にフェンスを待つ。ホスト非コヒーレントメモリは flush／invalidate。これは単一ステージング領域であり、複数フレームの並列リングバッファではない。
- `Texture9` は BGRA8 の CPU 側コピーと Vulkan 画像を持ち、ロック時に従来のピクセルを保持し、部分矩形の pitch は画像全体の行幅とする。READONLY と動的テクスチャ全体の DISCARD のみ対応、他のフラグは拒否。DISCARD 後の未定義データは実験版ではゼロにする。未対応の D3D9 形式・多段 mip・pool などは実装していない。
- 更新矩形をまとめ、`flush` で Vulkan 転送に変換する。ステージング容量を超える矩形は分割し、容量不足時にそれまでの転送を送って領域を再利用。画像は CPU 側でゼロ初期化するため、初回 `flush` は全体を送信する。
- RGBA8／BGRA8 の全画像を元のバイト順で同期的に読み戻す検査 API。BGRA8 は little-endian の D3DFMT_A8R8G8B8 のバイト順に対応するが、D3D9 の形式・リソース全体の実装ではない。実験用の境界検査と失敗通知。入力不正や容量不足は修正して再試行できるが、Vulkan エラー時はインスタンスを破棄して再作成する。

低レベル `UploadContext` の確保直後の画像は未定義であり、使用前に画像全体を初期化すること。`Texture9` はゼロ初期化し初回 flush 時に全体を転送する。ロックした CPU ポインタは unlock 後に保持してはならず、読み取り専用ロックで書き込んではならない。コンテキストは各 `Texture9` より長生きさせ、GPU 利用前に明示的に flush・submit する。各テクスチャはコンテキスト破棄まで保持する。固定 8 MiB の既定ステージング容量を使い切ると例外を返すため、利用側は送信してから再試行する。領域へのポインタは次の再利用後は保持してはいけない。複数スレッドからの同時利用は不可。

## ビルドと検査

C++17、CMake、Vulkan ヘッダーとローダー、Vulkan 実装が必要。

```sh
cmake -S experimental/gamenative-d3d9 -B /tmp/gn-d3d9 -DCMAKE_BUILD_TYPE=Debug
cmake --build /tmp/gn-d3d9
ctest --test-dir /tmp/gn-d3d9 -V --output-on-failure
```

GitHub Actions は lavapipe と Vulkan validation layer を使って部分更新、重複、複数画像、境界エラー、ロック状態とピッチ、容量を超える画像の分割転送、送信・再利用と読み戻したピクセルを確認する。別の Wine テストで実験用 DLL のロード・COM の参照カウント・未対応機能の失敗を確認する。これはゲームの描画や性能の検証ではない。

## 未実装

DLL のその他エクスポート、D3D9 デバイス／テクスチャ等の COM インターフェースと Vulkan 基盤の接続、デバイス・リソースのライフサイクル、D3D9 の LockRect 全フラグや全形式・pool・mip レベル、描画状態、シェーダーと固定機能、レンダーターゲット、ウィンドウ／swapchain／Present、デバイスロスト・Reset、同期やマルチスレッド、Android/Wine との統合、互換性試験。特に **D3D9 デバイス作成と描画を受け取る ABI 層はまだない**。これらを実装してから初めてゲームの比較が可能になる。性能対策は各機能の正確性と実測を伴って導入する。
